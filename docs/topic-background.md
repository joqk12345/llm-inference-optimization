# 选题背景与特色

**最后更新**：2026-07-13

## 为什么需要这本书

LLM 推理不是一次模型调用，而是一套持续运行的系统：请求进入队列，经过 prefill 和 decode，占用权重、KV Cache、计算、网络与调度资源，最后在延迟、质量、吞吐、可靠性和成本约束下交付结果。

公开资料通常分别回答某一个局部问题：论文解释机制，框架文档解释接口，硬件文档解释规格，案例文章解释某次实践。工程团队仍需要把这些材料连接成一条可执行路径：

1. 先定义工作负载、SLO、质量与成本口径；
2. 再定位计算、带宽、容量、调度或系统边界瓶颈；
3. 根据机制选择候选优化；
4. 用相同流量和回归集验证收益与副作用；
5. 把版本、假设、原始结果和回滚条件交给下一位维护者。

本书的目标，就是提供这套从机制理解到生产验证的共同语言。

## 内容边界

本书覆盖：

- GPU 计算、显存层级与 Roofline 思维；
- prefill、decode、Attention 与 KV Cache；
- 分页管理、前缀复用、调度与 PD 分离；
- 权重/KV 量化和投机解码；
- 服务部署、可观测性、容量实验与成本核算；
- MoE、混合状态和其他进阶架构。

本书不承诺：

- 某个框架对所有模型和硬件始终最快；
- 某项优化具有跨负载成立的固定加速比；
- 示例参数可以直接作为生产默认值；
- 论文 benchmark 可以替代业务质量和 SLO 回归。

## 写作与证据原则

### 系统问题优先

每项技术先回答它解决的是容量、数据移动、调度干扰、排队还是运维问题，再讨论具体实现。工具名称不能代替问题定义。

### 机制先于结论

正文先说明数据如何流动、资源如何增长、瓶颈如何形成，再给出候选优化。诸如“decode 常见为带宽敏感”只作为待验证假设，不作为无条件定律。

### 数字携带条件

性能与质量数字必须同时记录模型、制品 revision、硬件、精度、框架版本、输入/输出长度、并发、指标定义与数据来源。条件不完整时，只保留机制性结论。

### 区分四类代码

- **可运行示例**：给出依赖、输入和验证方式；
- **配置骨架**：使用明确占位符，必须按版本填充；
- **概念伪代码**：只解释机制，不声称对应内部 API；
- **教学算例**：展示公式，不冒充实测 benchmark。

### 版本敏感内容可回滚

生产示例需要锁定镜像 digest、依赖 lockfile、模型 revision 和启动参数。使用 `latest`、nightly 或私有内部 API 的内容不能被标为可复现生产方案。

## 学习路径

```text
第1–2章：动机、指标与技术地图
    ↓
第3–5章：GPU、环境、prefill/decode 与 Attention 基础
    ↓
第6–9章：KV、调度、量化与投机解码
    ↓
第10–11章：生产系统与进阶架构
    ↓
附录：工具、排障与待验证的 benchmark/ROI 模板
```

读者不需要在第一遍就寻找“最优配置”。更重要的是学会建立基线、提出机制假设、设计单变量实验，并知道结论在哪些条件下会失效。

## 维护方式

快速变化的框架能力放在版本敏感段落和来源卡中；相对稳定的计算机制、容量公式与验证方法留在正文主线。每次更新至少检查：

- 来源是否仍可访问，结论是否超出来源边界；
- 命令和指标名是否与锁定版本一致；
- 示例是实测、算例、骨架还是伪代码；
- 数字是否携带完整条件；
- 失败边界、开放问题与交接信息是否明确。

这本书的价值不来自“震撼数字”，而来自让推理优化决策更可解释、可验证和可交接。
